# 文旅营销素材生成设计

> 日期：2026-08-28
> 项目：project002文旅营销素材生成
> 状态：已确认，进入 PRD 实施拆解

## 1. 目标

面向文旅行业内部营销人员，提供一个极简的内容生成入口：用户选择模板并输入一句话需求，系统根据模板提示词调用文案模型和图片模型，返回一整套可直接发布的营销素材。

用户不需要理解提示词、模型或复杂参数。

## 2. MVP 范围

### 必须实现

- 前端提供四个模板选择：固定 IP 形象、旅游攻略知识卡片、风景拼图、人物拼图。
- 前端提供一句话输入框和一键生成按钮。
- Demo 阶段只接收文字，不提供参考图片上传。
- 后端校验模板编号和输入内容。
- 后端根据模板并行装配“用户可见文案提示词”和“视觉规划提示词”。
- 视觉规划结果按封面页、内容页、结尾页等页面角色拆分图片提示词，再调用图片模型。
- 前端展示标题、正文、标签和图片组。
- 支持分别复制标题、正文、标签。
- 支持下载单张图片和完整素材包。
- 使用占位提示词和 mock 模型时，项目可以在无外部模型密钥的情况下完整运行。
- 正式提示词接入时只修改模板文件或配置，不修改前端协议和生成主流程。

### 不做

- 登录、权限、历史记录、收藏和数据库。
- 多轮对话和自动规划型 Agent。
- 自动识别用户想使用的模板。
- 真实景区知识库和事实校验。
- 云端素材管理、二维码和社交平台自动发布。
- 视频生成。
- 图片生成后的字体替换、Canvas/SVG 二次排版和人工套版。

## 3. 用户流程

```text
打开页面
→ 选择一个内容模板
→ 输入一句话需求
→ 点击“一键生成”
→ 等待生成完成
→ 查看整套素材
→ 复制文字或下载图片/素材包
```

用户输入示例：

```text
为贵州夏季避暑旅游活动生成一套年轻人喜欢的宣传素材
```

## 4. 模板与输出

四个模板共用输出协议，差异只存在于两套提示词、生成步骤、页面数量和视觉规格。图片中的中文、艺术字体和文字排版均由图片模型按照视觉提示词完成，系统不做后置文字渲染。

| 模板 ID | 默认输出 | 默认图片形式 |
|---|---|---|
| `ip-image` | 标题、正文、标签、IP 主视觉 | 1 张主图 |
| `travel-cards` | 总标题、正文、标签、攻略卡片说明 | 4 张知识卡片 |
| `scenery-collage` | 标题、正文、标签、景点卖点 | 1 张风景拼图 |
| `people-collage` | 标题、正文、标签、旅拍卖点 | 1 张人物拼图 |

后续队友可以调整图片数量、比例和提示词，但不能破坏统一输出协议；确需扩展字段时新增可选字段，不改变既有字段语义。

## 5. 数据协议

### 生成请求

```ts
type GenerateRequest = {
  templateId: string;
  userPrompt: string;
};
```

约束：`templateId` 必须来自后端已注册模板；`userPrompt` 去除首尾空白后不能为空，长度限制为 2—500 个字符；前后端都执行校验。

### 生成响应

```ts
type GenerateResponse = {
  requestId: string;
  templateId: string;
  status: "succeeded" | "partial";
  copy: {
    title: string;
    body: string;
    tags: string[];
  };
  pages: Array<{
    id: string;
    pageType: "cover" | "content" | "ending";
    filename: string;
    status: "succeeded" | "failed";
    imageUrl?: string;
    alt?: string;
    error?: string;
  }>;
  warnings: string[];
};
```

`warnings` 用于报告图片生成失败、使用 mock 内容等非致命情况；文案失败时请求失败，部分图片失败时返回 `partial`，保留已生成文案和成功页面。

## 6. 系统架构

```text
React 前端
  ├─ 模板选择
  ├─ 一句话输入
  ├─ 生成状态
  └─ 素材包展示/复制/下载
          ↓ HTTP
Node.js TypeScript 后端
  ├─ Generate API
  ├─ 模板注册表
  ├─ 文案提示词构建器
  ├─ 视觉规划提示词构建器
  ├─ 文案模型适配器
  ├─ 图片模型适配器
  ├─ 页面级图片任务编排
  └─ 素材包响应整理
```

核心边界：

- 前端只提交 `templateId` 和 `userPrompt`，不接触完整提示词和模型密钥。
- 模板模块只负责定义模板信息、提示词和生成策略。
- 模型适配器只负责把统一请求转换为具体模型调用，不承载业务模板规则。
- 生成服务负责编排模板和模型，不直接写前端展示逻辑。
- MVP 不保存用户输入和生成结果；素材通过本次响应提供给前端。

## 7. 模板接口

```ts
type TemplateContext = {
  userPrompt: string;
};

type GeneratedCopy = {
  title: string;
  body: string;
  tags: string[];
};

type VisualPagePlan = {
  id: string;
  pageType: "cover" | "content" | "ending";
  imagePrompt: string;
  filename: string;
};

type VisualPlan = {
  pages: VisualPagePlan[];
};

type MarketingTemplate = {
  id: string;
  name: string;
  buildCopyPrompt(context: TemplateContext): string;
  buildVisualPlanPrompt(context: TemplateContext): string;
};
```

正式提示词到位后，由队友分别替换 `buildCopyPrompt` 和 `buildVisualPlanPrompt` 的内容；视觉规划提示词负责规定每一页的画面、页面文字、艺术字体、字号层级、构图和排版。四个模板之间保持独立。

## 8. 生成策略

- 用户可见文案和视觉规划默认由两个提示词分支并行生成，二者共享同一个模板和用户输入。
- 视觉规划模型必须返回页面数组，每个页面包含可直接传给图片模型的完整提示词。
- 图片提示词中包含需要展示的页面文字、艺术字体和排版要求；图片模型直接生成完整页面，系统不做文字叠加。
- 多个页面的图片任务并行生成，单页失败不取消其他页面。
- 架构允许模板未来切换为“先文案、后视觉规划”，但不改变前端请求和响应协议。
- 首版默认使用 mock provider，返回确定性的演示结果；配置真实 provider 后使用环境变量读取模型地址和密钥。
- 真实 provider 的返回结果必须先转换为统一的 `GeneratedCopy` 和图片结果，再返回 API。

## 9. 异常与状态

- 空输入或超过长度：前端阻止提交，后端返回 `400`。
- 不存在的模板：后端返回 `400`，前端提示模板不可用。
- 文案模型失败或超时：返回 `502`，前端保留输入并允许重试。
- 图片模型失败：返回文案和 `warnings`，前端显示图片失败提示。
- 部分页面失败：成功页面正常展示和下载，失败页面显示状态并允许整套重新生成；MVP 不做单页重试。
- 生成中：按钮禁用并展示明确的加载状态，防止重复提交。
- 下载失败：不影响生成结果，前端提示用户单独下载图片。

## 10. 验收标准

- 四个模板均可被选择并成功提交。
- 输入一句话后，mock 模式能返回标题、正文、标签和对应图片数量。
- 文案与视觉规划两个提示词分支能够独立替换，并默认并行执行。
- 图片页面的文字、艺术字体和排版要求由图片提示词表达，系统无后置排版逻辑。
- 结果页能分别复制标题、正文、标签。
- 结果页能下载图片，并能下载包含图片和文案的素材包。
- 重复点击不会产生并发重复请求。
- 无模型密钥时可以启动并完成 mock 端到端流程。
- 替换单个模板提示词不会修改其他模板和公共 API。
- 任意一个图片页面模拟失败时，其余页面和完整文案仍正常返回，响应状态为 `partial`。
- 前端构建、后端测试和接口冒烟测试通过。

## 11. 后续扩展边界

后续新增文旅模板或其他行业模板时，只增加模板定义、模型策略和必要的展示字段；登录、历史、知识库、参考图上传、固定 IP 跨次一致性、发布渠道适配属于独立版本，不进入本次 MVP。
